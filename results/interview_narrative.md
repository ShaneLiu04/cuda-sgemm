## 0. 三十秒电梯陈述

"我在一台 Quadro RTX 5000（Turing sm_75，48 SM）上从零写了十七版严格 FP32 的 SGEMM kernel——
不允许 TF32、不允许快速数学——从教科书版的 157 GFLOPS 一路做到 2048³ 的 8,773 GFLOPS
（cuBLAS 的 84.85%，尾波税消除 +2.35pp），4096³ 是 9,058（%peak 78.0）；256³ 小尺寸稳定
反超 cuBLAS 22.2%，1024³ 刀锋差 cuBLAS 0.10 个百分点。十七版里九版关键假设被**实测否定**
（含"Stream-K 多波精确填充"这个我最看好的假说），我照样归档——因为它们指出了下一版
该往哪走。全程每个数字带 git sha、时钟、温度，任何一个历史点都能复现。"

**追问点预判**：为什么 85% 而不是 90%（split 结构税 + LDS.128 带宽墙，§故事 7/8b）；为什么小尺寸能反超
（库的尺寸自适应开销区，§故事 5）；凭什么说"严格 FP32"（双参考交叉验证 rel≈1e-7，TF32 会掉到 1e-3 量级）。

## 1. 主线故事（STAR × 优化层）

### 故事 1：从 157 到 792——先修访存模式，再谈别的（K0→K1）

- **S/T**：naive kernel 每线程一个输出、按行 stride 访问，4096³ 只有 157 GF，等于峰值的 1.3%。
- **A**：不急着"优化"，先算账：有效带宽 0.23 GB/s，延迟受限。交换线程到输出的映射，
  让 B/C 按线程连续（合并 128B 事务），A 走广播。
- **R**：同流量下事务数 32→4，792.4 GF（5.05×）。**教训锚点**：先测量、后优化；
  教科书 kernel 的问题不是"算得慢"而是"喂不饱"。

### 故事 2：roofline 逼出来的 smem 分块（K2）

- **S/T**：K1 后内存顶在眼前：该尺寸算法强度下，2874.7 GF 就是带宽天花板。
- **A**：用算法强度模型（不是猜）证明：不提高数据复用，物理上不可能更快。上 32×32×32
  tile 经 shared memory 复用 ×32。
- **R**：2,874.7 GF = 其算法强度内存顶的 **95.7%**——roofline 模型说满了，下一版必须提高算术强度。

### 故事 3：寄存器外积 + 向量化，两步拆掉 smem 瓶颈（K3→K4）

- **S/T**：K2 贴内存顶后瓶颈切换到计算侧：smem bank conflict。
- **A**：K3 上 128×128×8 分块 + 每线程 8×8 寄存器外积（AI 8→31.5 FLOP/B）；
  K4 上 LDS.128 向量化 + A 转置 + B 的 XOR swizzle，**先在纸上算冲突模式再改代码**。
- **R**：4,683.6 → 6,391.3 GF。**方法论锚点**：bank conflict 不靠感觉，靠模型预测 + 实测对照。

### 故事 4：cp.async 负结果——架构文档决定指令边界（K5）

- **S/T**：教科书下一步都是 cp.async 双缓冲，社区教程在 sm_75 上也这么教。
- **A**：实测 -12%。查架构：**cp.async 是 sm_80（Ampere）指令**，sm_75 上头文件静默退化成同步拷贝。
- **R**：负结果归档（5,647.1 GF），但消融证明"寄存器预取无害"→ 直接孵化 K6 软件流水
  （LDG 提前一轮入寄存器，+4.7%，六尺寸全胜）。**面试金句**：负结果不是失败，
  是排除了一个假设、指出了正确假设的方向。

### 故事 5：split-K 解 wave 饥饿 + 小尺寸反超 cuBLAS（K6'）

- **S/T**：512³ 时 48 SM 只有 16 个 128×128 block——1/3 的 SM 在空转（wave 饥饿）。
- **A**：split-K 把 K 维切 3-6 片，中间结果写 workspace、二次确定性归约；
  sk 按尺寸实测回填（256³→sk6，512³→sk3）。
- **R**：512³ +49.4%；256³ 同钟态同会话 1,551.2 GF vs cuBLAS 1,258.0——**反超 23.3%**
  （auto dispatch 1,555.8 = +23.7%）。**洞察锚点**：小尺寸是库的"尺寸探测开销区"，
  自研 kernel 没有这个税——这是自研 kernel 的天然领先窗口。

### 故事 6：两个"看起来对"的设计被消融否定（K7/K8）

- **S/T**：warp 专属化（producer/consumer）和 512 线程宽块都是主流优化方向。
- **A**：各做三轴消融（PW/STAGES/LB 8 配置；launch_bounds 扫描）。
- **R**：ws 5,377.7 / wide 4,408.8，均低于 6,584.8 基线；wide 100% warp slots 占用仍
  0.57-0.75× 于最优——**占用率不是 FP32 吞吐的杠杆**，真墙是 LDS.128 带宽。
  这个否定直接决定了 K9 的形态。

### 故事 7：deep/dsk——反直觉的 128 累加器设计（K9）

- **S/T**：占满 SM 的直觉被证伪后，需要新设计原则：降 LDS 频率、波次精确。
- **A**：BM256×BN128×BK8，每线程 16×8=**128 个 FMA 累加器**，247 寄存器 0 spill
  （256 线程 × 247 = 63,232，恰满 64K 寄存器堆，1 block/SM）；A 行驻寄存器、B 列 smem 广播、
  smem 双缓冲；1024³ 下 32 tiles × sk3 = 96 blocks = **精确 2 波**。
- **R**：2048³ 8,568.5 GF（%peak 72.1，同会话 cuBLAS 82.6%）；1024³ dsk 74.77% 刀锋。
  1 block/SM = 25% 线程占用率反而是最优——**这是"占用率迷信"最有力的反例**。

### 故事 8：ptxas 寄存器重排陷阱——一个"无害小改动"损失 4.9%（AR010 核心发现）

- **S/T**：给 split-K 加"末片直写 C"时，用运行时参数选择输出指针——功能正确、逻辑无害。
- **A**：性能 -4.9%（main 段 5,017 vs 5,270 GF）。查 `-Xptxas -v`：ptxas 因双指针跨主循环
  活跃，把 247/241 寄存器布局重排成 243——**不是 spill，是"合法但更差"的分配**。
- **R**：改成 `template <int DBUF, int LAST_DIRECT>` 编译期实例化 + Out 指针计算下沉到回写段，
  247/243 各归其位，dsk 创历史最佳 6,312-6,321 GF（1024³ 热态探针）。
  **金句**：寄存器敏感 kernel 上没有"无害小改动"——每次改动都要过 ptxas 审计；
  性能回退先看资源报告，不急着怀疑算法。

### 故事 8b：Stream-K——我最看好的假说被否定，但机制照样兑现（K10）

- **S/T**：2048³ deep 是 2.67 波（128 tiles / 48 SM），尾波空转 ~11%——教科书答案就是
  Stream-K 多波精确填充：把 K 切开让 grid 恰好凑整波。
- **A**：实现 tile-major 工作包统一调度（票据累加确定性归约 + solo 快路径 + 融合归约，
  255 regs 0 spill），然后 W{1..8} × 六尺寸 × 3 轮全扫（165 行实测）。
- **R**：**假说否定**——W=2 整波（96 blocks = 2 精确波）8,355 GF 反而低于 deep 2.67 波
  8,542 GF；赢面在 **W=1 tile 聚合**（48 blocks 恒 1 波 + solo 免票据）：8,773-8,784 GF
  = cuBLAS 的 **84.85%**（尾波税 +2.35pp 兑现，G6 85% 门差 0.15pp ≈ 3.2μs，刀锋 MISS
  门线不放宽）。**金句**：机制兑现和门通过是两回事——把假说否定、机制兑现、门差 0.15pp
  三件事分开讲清楚，比"过了"更有信息量。

## 2. 测量方法学故事（最能区分"跑过 demo"和"做过性能工程"的部分）

### 故事 9：WDDM 时钟漂移与 %peak 不变量

- **S**：Windows + WDDM 没有 `nvidia-smi -lgc` 锁频权限；同一 kernel 早跑 8,100、晚跑 7,600，
  跨会话数字不可比；重核触发 boost 1,920-1,950 MHz 而小突发核保持 1,620——**同会话两种钟态并存**。
- **A**：定义 **%peak = GFLOPS / (6144 × SM时钟)**，钟频线性假设用 boost 实测锚定
  （6,296@1620 → 7,276@1950，比率误差 0.1%）；比例门全部改成**同会话背靠背锚定 cuBLAS 分母**；
  配对协议加 GPU 唤醒 spin + 47°C 冷却门 + boost 轮剔除。
- **R**：cuBLAS 分母自身热态摆幅 ±0.65% 成为比例门的测量下限——1024³ 刀锋 74.77%
  的 0.23pp 缺口就在这个下限里。**金句**：测不准分母，就别下"谁更快"的结论；
  先把测量系统的误差棒算出来。

### 故事 10：逐位等价——split-K 优化不许动数值

- **S/T**：归约路径改了三版（v2 ILP2 / v3 ILP4+流式 / 末片直写），任何一版改变浮点加法顺序都会
  改结果。
- **A**：设计上保证加法链同序（末片直写只是把"末片→P→归约"折叠成"末片→C"，归约少读一片 P
  但加法次序不变）；再建 21 例逐位等价专项测试（BK=8 同切分 + 单一归约入口 + 三重锚点 +
  确定性双跑）。
- **R**：21/21 逐位相同，性能优化和数值不变性同时成立。**金句**：浮点优化做到最后，
  "和原来一样"必须是可以**逐位证明**的，不是"误差看起来很小"。

### 故事 11：1024³ 刀锋 FAIL——把 0.23pp 讲成完整因果链

- **S/T**：74.77% vs 75% 门——差 0.23pp，看似"差一点就过"。
- **A**：六变体攻坚链全实测：会话偏移修正（识别跨会话混搭伪影 +0.5%）→ 归约 v3（仅省 1.5μs，
  流量地板 355 GB/s ≈ DRAM 峰 80-90%）→ `__stwt` 写穿（负结果 +16μs）→ 末片直写（+1.1%）→
  ptxas 重排修复（+3.4%）→ 模板化终态 6,312-6,321 GF 热态。
- **R**：门判 **FAIL 不放宽**——0.23pp 小于 cuBLAS 分母自身摆幅 ±0.65pp，已到"分母测量下限"；
  剩余杠杆（L2 persistence、单核确定性归约）明示进 backlog。**金句**：门就是门；
  但把"为什么差、差在哪、还剩什么杠杆"讲清楚，比"放水通过"值钱得多。
  （AR011 终态：责任链再补三环——L2 persistence 能力墙 N/A、BPF/PHASE 双因子负、
  streamk@1024³ = dsk 的 87%；74.77% → 74.90%，缺口 main ~42μs + reduce ~43μs 结构性。）

### 故事 11b：冷锚会把 MISS 变伪 PASS——锚敏感性与时钟制度纪律（AR011）

- **S/T**：2048³ 的 cuBLAS 分母三轮里从 9,278 到 10,343 摆 11%——判 85% 门时分母选错
  9.8pp 就没了；K=4096 尺寸还有冷启动 1,620 vs in-seq 热 1,920-1,935 MHz 的 -13% 制度差。
- **A**：协议加 cublas 首末双锚（末锚三轮 10,337-10,342 rock-stable 作有效分母）；
  r1 冷锚 9,278 识别为轮首冷启动压制值排除；K=4096 保真验证改逐行冷却协议。
- **R**：G6 判定 84.85% MISS（差 0.15pp）——若误用 r1 冷锚会得 94.67% 伪 PASS。
  **金句**：比例门的双向陷阱——分母被压低出伪 PASS、被抬高出伪 FAIL；
  锚的稳定性本身要当数据来审计。

## 3. 工程协作故事（流程/工程化）

### 故事 12：git-ai 推送被 WAF 掐——把踩坑变成团队资产

- **S/T**：向 gitee 推送时随机 403，且**同会话内时好时坏**，极像玄学。
- **A**：控制变量法定位：合成小探针成功 → 排除鉴权；量化图片后成功 → 锁定 POST 包体积；
  最终结论：BDWAF 掐 >~100KB 的 HTTPS POST（含 git 的 packfile 协商包）。再发现
  **同拓扑分支的树对象不会被 push 协商排除，只有祖先链生效**——大内容必须逐组在目标父链上推送。
- **R**：沉淀三条团队规则：图表全部量化 ≤72KB（`make_figures.py` 量化管线，从 CSV 可复现）、
  文本提交天然小包安全、大内容走分组传输协议。**金句**：排除法 + 控制变量不只用于 kernel，
  也用于工程环境本身。

### 故事 13：AI 结对开发的纪律（如何让 AI 不毁掉数据真实性）

- **S/T**：全程用 AI agent 结对开发 CUDA，最大的风险不是代码错，是**性能数据被编造/污染**。
- **A**：AGENTS.md 立军规——数据真实性第一：所有 benchmark 只用 CUDA events、CSV 每行带
  git sha/时钟/温度/功耗、非默认参数分流独立 CSV 禁止污染主数据、负结果同等归档、
  门判定不允许"看起来差不多就过"。
- **R**：AR001-AR010 十个迭代、28 张图、数百行 CSV 全部可复现；两次"数据事故"（CSV 重复追加、
  跨会话混搭）都被军规流程自己抓出来修正。**金句**：AI 结对开发的产出质量上限，
  取决于你给它的约束有多硬。

## 4. "如果重来一次"（诚实的复盘，面试官最爱问）

1. **早点建测量基础设施**：前两个 AR 用裸会话跑数，后来发现跨会话不可比，被迫补配对协议与
   %peak 归一重测。如果一开始就同会话锚定 cuBLAS，能省两次返工。
2. **ptxas 审计应该从第一版就是硬门**：AR010 的寄存器重排陷阱（-4.9%）说明资源报告
   该是每次提交的必检项，而不是出问题才看。
3. **负结果的消融可以更早设计**：ws/wide 两个负结果各花了整个 AR 的力气；如果消融矩阵
   （PW×STAGES×LB）在方案期就排好，可以更快收敛到"占用率非杠杆"的结论。
4. **1024³ 的 L2 persistence 该早点试**：归约流量地板分析其实早就指出 C 读被 A/B 流驱逐，
  persistence window 是少数还没动的系统级杠杆。
5. **不过有一个不后悔**：坚持严格 FP32 不开 TF32——这让所有数字都有"IEEE 语义"背书，
  正确性验证（rel≈1e-7）与逐位等价测试才有意义。

## 6. 高频追问的标准答案（背熟数字）

- **Q: 最高多少 GFLOPS？峰值百分比？**
  A: 2048³ 8,773 GF = cuBLAS 的 84.85%（%peak 74.4 @1920 MHz）；4096³ 9,058 = %peak 78.0。
- **Q: 和 cuBLAS 差多少？**
  A: 同会话配对：2048³ 84.85%、4096³ 88.2%、1024³ 74.9%、512³ 75.0%、256³ **反超 22.2%**。
- **Q: 提升了多少倍？**
  A: 对 naive 基线 157 GF：4096³ 57.7×、2048³ 55.9×。
- **Q: 怎么保证没作弊（TF32/快数学）？**
  A: 编译禁 fast_math、运行时断言 math mode、CPU double + cuBLAS 双参考交叉验证
  （rel≈1e-7，TF32 会是 1e-3 量级）、split-K 逐位等价 21/21。
- **Q: 正确性怎么验的？**
  A: 163 例全 kernel × 尺寸/边界/回退；compute-sanitizer memcheck 全绿、racecheck 0 hazards。
- **Q: 最大的教训？**
  A: 四个候选任讲：占用率迷信（数据否定直觉）、ptxas 重排（0 spill 也能掉 4.9%）、
  多波精确填充假说否定（最看好的方案被 165 行 sweep 推翻）、
  测量先于优化（WDDM 漂移曾让跨会话数字全废；冷锚曾差点把 MISS 变伪 PASS）。
